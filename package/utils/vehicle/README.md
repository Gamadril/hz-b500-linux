# Vehicle data service

Reads the BMW E90 CAN bus through an added bridge, decodes it and publishes the
state over ubus for the HMI, the parking-sensor view and Android Auto.

```text
ESP32 bridge -> UART3 -> vehicle-slcan -> can0 -> vehicled -> ubus -> HMI, PDC view
                                                            `-> vehicle-watch -> wheel keys -> Android Auto
```

## Bridge wiring

An ESP32-C3 Super Mini with an SN65HVD230 transceiver connects to header J6:
PB6 is F133 TX, PB7 is F133 RX (UART3, `/dev/ttyS3`). The bridge listens on the
CAN bus (100 kbit/s, listen-only) and forwards frames as SLCAN at 750000 baud.
Nothing is ever transmitted to the car. See the
[Hackaday project](https://hackaday.io/project/205793-reverse-engineering-f133d1s-device)
for the modification.

## Service

`/etc/init.d/vehicle` starts at boot. Configuration in `/etc/config/vehicle`:

| Option | Default | Meaning |
| --- | --- | --- |
| `enabled` | `1` | Run the service |
| `device`, `baud` | `/dev/ttyS3`, `750000` | Bridge UART |
| `interface` | `can0` | SocketCAN interface |
| `attach_slcan` | `1` | `0` if `can0` is set up externally |
| `media_keys` | `1` | Forward steering-wheel keys to Android Auto |
| `fuel_capacity_litres` | `63` | Tank size for the fuel gauge |

Apply changes with `/etc/init.d/vehicle restart`. On the device:

```sh
ubus call vehicle snapshot     # current state
vehicle-watch                  # follow changes
```

Each signal has `valid`; `false` means unknown or too old, and the HMI then
hides that value. The first valid date/time from the car sets the system clock
(Europe/Berlin by default). `/var/run/vehicle/night` is `1` while low or high
beam is on, used for LCD dimming and Android Auto night mode.

## Decoded signals

| CAN ID | Signal |
| --- | --- |
| `0x1A6` | Speed |
| `0x0AA` | Engine RPM (`FF FF` with engine off = unavailable) |
| `0x1D0` | Coolant temperature |
| `0x349` | Fuel level |
| `0x1D2` | Manual gear, generated by the bridge (`R`, `N`, `1`–`6`) |
| `0x21A` | Headlights (off / low / high) |
| `0x1F6` | Turn signals |
| `0x2FC` | Doors and trunk |
| `0x193` | Cruise control |
| `0x24A`, `0x1C2` | Parking sensors (active state, eight distances) |
| `0x2F8` | Date and time |
| `0x1D6` | Steering-wheel media keys |

Confirmed in the car: RPM and headlights. Coolant and fuel have not been
compared with the car's gauges yet.

## Testing without a car

**Desktop simulator** (no board needed):

```bash
bash package/utils/vehicle/build-host.sh --fetch-deps
bash package/utils/vehicle/simulate.sh
export VEHICLE_UBUS_SOCKET="$PWD/out/vehicle/simulator/ubus.sock"   # other terminal
bash package/gui/car-dashboards/run-host.sh hmi --vehicle
```

**UART bridge simulator:** a USB serial adapter replaces the ESP32 (adapter TX
to PB7, common GND) and feeds the real board:

```bash
bash scripts/vehicle-uart-sim.sh --device /dev/ttyUSB0                  # speed/RPM sweep
bash scripts/vehicle-uart-sim.sh --device /dev/ttyUSB0 --speed 80 --rpm 2500 --lights low
bash scripts/vehicle-uart-sim.sh --stdout --count 1 | tr '\r' '\n'      # show frames only
```

`--lights off|low|high` also sends headlights (night mode); `--count 0` runs
until Ctrl-C. `--help` lists all options.

## No readings on the board?

`can0` exists even without a bridge; values stay unknown until frames arrive.
Check, with the bridge connected and the car awake:

```sh
ubus call vehicle snapshot
cat /sys/class/net/can0/statistics/rx_packets
cat /proc/tty/driver/uart
```

Rising `rx_packets` with no `received_frames` in the snapshot means the frames
are not ones the service decodes.
